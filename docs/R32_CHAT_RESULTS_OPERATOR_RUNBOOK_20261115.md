**เขตงาน:** กีฬา “มิตรภาพเกมส์ 2569” เท่านั้น. ไม่ใช่คู่มือระบบประชุม Meeting. พื้นที่ `nongkum_sports` เป็น schema ภายใน Supabase Meeting ที่ไม่เปิดเผยผ่าน Data API.

**สถานะ ณ 15 พ.ย. 2569:** DB migration R32-A + R32B applied แล้ว, ไฟล์ร่าง 0, ผลรับรอง 0, ประวัติการรับรอง 0. หน้าเว็บ R32-B อยู่ใน PR #142; ยังไม่ได้ Merge/ตรวจรับอุปกรณ์จริง. Google Sheets เดิมยังเป็นช่องทางคู่ขนานที่ไม่ได้เชื่อมเข้าฐาน R32 อัตโนมัติ.

## งานที่ผู้จัด/ChatGPT ทำได้ทันที (เมื่อมีผลจริงและหลักฐาน)

1. ผู้ประสานงานส่ง **ภาพใบคะแนนหรือข้อความผลจริง** ในแชท ChatGPT พร้อมระบุชนิดกีฬา/รุ่น/โรงเรียนหากภาพไม่ชัด. หลักฐานภาพเป็นทางเลือกในกรณีปกติ แต่กรณีขัดแย้งหรือแก้คะแนนต้องมีหลักฐานชัดเจน.
2. ChatGPT ช่วยถอดคะแนนและตรวจ `fixture_id` / `event_id` เทียบกับ **รายการได้รับรองล่าสุด** ใน `main` และเอกสารผู้จัด (รวมคู่ที่ถูกตัดซ้ำ); ห้ามเดาผล / เวลา / คู่แข่ง. ถ้าพบข้อมูลขัดแย้ง ให้หยุดและรายงานก่อน.
3. ใช้ **Supabase connector สำหรับผู้ดูแลที่ได้รับอนุญาต** บันทึกลง `nongkum_sports.result_submissions` พร้อม revision, `source_ref` (เอกสาร/commit อ้างอิง), `received_via='chat'`, `submitted_by` และ `evidence_ref` ในพื้นที่จำกัดสิทธิ์. ใบคะแนนต้นฉบับต้องเก็บส่วนตัว (เช่น Drive ที่จำกัดสิทธิ์); **อย่าใส่ลายเซ็น/ข้อมูลเด็ก/ลิงก์ส่วนตัวในข้อมูลหน้าเว็บ**.
4. แจ้งผู้จัดว่า **“บันทึกแล้ว รอตรวจสอบ”**; ยังไม่แสดงสาธารณะ. ให้ผู้มีสิทธิ์รับรองตรวจรายการ คะแนน ผู้ชนะ/อันดับ และหลักฐาน, รวมถึงความถูกต้องของรุ่น/คู่แข่ง.
5. หลังได้รับ **การรับรองที่ชัดเจนจากมนุษย์** และมีชื่อ/หลักฐานอ้างอิงการอนุมัติ ให้ผู้ดูแลเรียกฟังก์ชัน `nongkum_sports.approve_and_publish` ผ่านการเชื่อมต่อแบบ server-only/เครื่องมือบริหาร; ต้องระบุ `submission_id`, `expected_revision`, `approved_by`, `approval_ref`, และ `correction_note` สำหรับการแก้ไข. ฟังก์ชันตรวจสถานะ `review`, ตรวจ revision/source, คัดฟิลด์ส่วนตัวออก, และบันทึกประวัติ+ผลเผยแพร่ใน transaction เดียว. **AI ไม่ใช่ผู้มีสิทธิ์รับรองแทนมนุษย์**.
6. หน้าผลการแข่งขันเรียกตาราง `public.nongkum_published_results` ที่เปิดอ่านอย่างเดียว; หากเปิดผ่าน PR R32-B หลัง Merge ให้รีเฟรชหน้า/รอรอบตรวจข้อมูลใหม่ (~60 วินาที ขณะหน้าเปิดอยู่) และตรวจว่าเว็บไซต์แสดงผลตรงหลักฐาน. ไม่ใช่การประกาศผลก่อนมนุษย์รับรอง.

### รูปแบบตัวอย่างคำสั่งของผู้ดูแล (ใช้เฉพาะเมื่อมีข้อมูลจริงเท่านั้น)

การรับผลรอตรวจ: ใช้คำสั่ง `INSERT INTO nongkum_sports.result_submissions (...)` โดยกำหนด `result_id, fixture_id/event_id, sport_id, result_type, proposed_result, revision, status='review', received_via, source_ref, submitted_by, evidence_ref`. จด `id` ของแถวที่บันทึก. ห้ามนำข้อมูลคะแนนตัวอย่างใด ๆ ลงฐานจริง.

การรับรอง (เฉพาะหลังมีผู้รับรองและเอกสารอ้างอิงจริง):
```sql
select nongkum_sports.approve_and_publish(
  :submission_id, :expected_revision,
  :approved_by, :approval_reference,
  :correction_note
);
```
**สำคัญ:** ฟังก์ชันนี้ไม่แยกพิสูจน์ตัวตนของ `:approved_by` ในฐานข้อมูลเอง เพราะเป็นเครื่องมือบริหารแบบ server-only ผู้ใช้งานเครื่องมือจึงต้องตรวจสิทธิ์และหลักฐานการอนุมัติของมนุษย์ก่อนเรียก. ไม่เปิดใช้ฟังก์ชันนี้จากเว็บสาธารณะโดยตรง. สำหรับหน้าบันทึกผลของกรรมการหลายคนในอนาคต ต้องทำ Auth+RBAC ก่อนเปิดให้ใช้.

### แก้ไขผลหลังเผยแพร่
- สร้างรายการรอตรวจ **revision ใหม่** ไม่เขียนทับผลเก่าเงียบ ๆ; ผู้รับรองต้องบันทึกเหตุผลและหลักฐานการแก้ไข.
- ฟังก์ชันไม่ยอมรับ revision เก่ากว่าหรือซ้ำกับผลที่เผยแพร่แล้ว.
- เก็บ `result_approval_audit` ทั้งผลก่อนหน้า/ผลใหม่ พร้อมผู้รับรองและเหตุผลในพื้นที่ส่วนตัว; ประชาชนเห็นผลรุ่นล่าสุดเท่านั้น.

### การใช้ Google Sheets และ JSON สำรอง
- แผน R20 สำหรับ Google Sheets ยังอยู่ ไม่อ้างว่า Apps Script ติดตั้งจริงแล้ว. เมื่อเชื่อม Sheets ภายหลัง จะต้องส่งเข้าคิว `result_submissions` เดียวกัน ตรวจรหัส/รุ่น/การรับรองก่อนเผยแพร่.
- ไฟล์ `data/public-results.json` เป็น snapshot สำรองที่ตรวจ approved-only. หากเชื่อมฐานไม่ได้ หน้าเว็บแสดงข้อความว่าอ่าน **สำเนาผลที่รับรอง** และไม่อ้างว่ากำลังแสดงผลล่าสุด.
- หน้า `standings.html` ไม่แสดงอันดับที่กติกายังไม่รับรอง แม้มีผลแข่งขันที่รับรองแล้ว.

### ข้อควรระวังและงานค้าง
- โครงการ Meeting มีคำเตือน Security Advisor เดิมบางรายการที่เกี่ยวกับฟังก์ชันสิทธิ์สูง ไม่ใช่สิ่งที่ R32 สร้างขึ้น. ต้องตรวจแยกภายหลัง; R32 ไม่แก้/ไม่เปิดสิทธิ์ Meeting เดิม.
- PostgreSQL database อยู่ที่ Mumbai จึงควรวัดเวลา API บนมือถือไทยจริงก่อนอ้างว่าเร็วขึ้นเป็นวินาที.
- R32 ยังเป็นการเปิด **read-only public bridge + server-admin intake workflow**; ยังไม่มีหน้าเจ้าหน้าที่บันทึกผลด้วยบัญชีจริงและไม่มี realtime push (ในรุ่นนี้ตรวจข้อมูลใหม่ทุก 60 วินาที).
- ก่อน Merge PR ต้องให้ CI ผ่านทุกชุด; หลัง Merge ต้องตรวจ GitHub Pages, iPhone Safari, Android Chrome, LINE browser, และทดสอบข้อมูลผลจริงที่ผู้จัดรับรองแล้ว โดยไม่สร้างผลปลอมในฐาน production.
