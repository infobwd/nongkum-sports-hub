## 2. การใช้งานที่ผู้จัดต้องการ (UX)

### หน้า “ตารางแข่งขัน”
1. การ์ดคู่แข่งขันแสดงกีฬา รุ่น โรงเรียน วัน/เวลา/สนามตามต้นฉบับ และสรุปผลที่ **รับรองเผยแพร่แล้ว** เมื่อมีผล
2. ผู้มีสิทธิ์แตะบริเวณการ์ดเพื่อเปิดแบบบันทึก หรือใช้ปุ่มพร้อมรูปดินสอ **“บันทึกผล”** บนการ์ด; ถ้ามีผลรับรองแล้วใช้ **“แก้ไขผล”**; ปุ่มแชร์/สูจิบัตร/เอกสารต้องทำงานเหมือนเดิมและไม่กระตุ้นฟอร์มโดยไม่ตั้งใจ
3. ผู้ชมทั่วไปใช้ดูคู่และผลตามเดิม ไม่ถูกบังคับเข้ารหัสเมื่อเปิดดูรายการ; เส้นทางแก้ไขเท่านั้นที่ต้องตรวจสิทธิ์

### หน้า “ผลการแข่งขัน”
1. การ์ดผลรับรองมีตำแหน่งปุ่ม **“แก้ไขผล”** สำหรับผู้มีสิทธิ์ ข้าง/ใต้ปุ่มแชร์ตามขนาดมือถือ
2. ใช้ฟอร์มเดียวกันทั้งสองหน้า ส่ง ID คู่/รายการที่ถูกต้องจากการ์ด (ไม่ให้ผู้ใช้กรอกรหัส ID เอง)
3. หน้าเผยแพร่ยังแสดงผลที่รับรองล่าสุดระหว่างรอตรวจคำขอแก้ไข และมีป้ายสถานะเฉพาะเจ้าหน้าที่ให้เห็นว่า “มีรายการแก้ไขรอตรวจ”

### กล่องกรอกรหัส
- เมื่อเข้าทาง “บันทึกผล/แก้ไขผล” **ครั้งแรกบนเครื่อง** ถ้ายังไม่ได้ปลดล็อก จึงแสดงกล่องใส่รหัสแบบซ่อนตัวอักษร พร้อมปุ่ม “เข้าใช้งาน” และ “ยกเลิก”
- เมื่อกรอกถูกต้อง ระบบปลดล็อกสิทธิ์ให้ **6 ชั่วโมงนับจากเวลาตรวจรหัสสำเร็จ** (หมดอายุแบบตายตัว ไม่ขยายเวลาอัตโนมัติทุกครั้งที่แตะการ์ด)
- ระหว่าง 6 ชั่วโมง เปิดหน้าอื่น รีเฟรช หรือกลับเข้าหน้าเว็บในเบราว์เซอร์/บริบทเก็บข้อมูลเดียวกัน สามารถบันทึก/แก้ไขโดยไม่กรอกรหัสซ้ำ
- ครบ 6 ชั่วโมงออกจากสิทธิ์แก้ไขอัตโนมัติ; กดครั้งถัดไปให้กรอกรหัสใหม่; ปุ่ม **“ออกจากโหมดบันทึกผล”** ใช้ยกเลิกก่อนครบเวลาได้
- แสดงข้อความสั้น เช่น “ใช้งานบันทึกผลได้อีก 2 ชม. 10 นาที”; แสดงเวลาที่เหลือจาก `expires_at` ของฝั่งเซิร์ฟเวอร์ ไม่เชื่อการปรับนาฬิกาเครื่อง
- Safari, Chrome, เบราว์เซอร์ใน LINE และ PWA อาจมีที่เก็บข้อมูลคนละพื้นที่; **ไม่รับประกัน** ว่าปลดล็อกจากแอปหนึ่งจะใช้ได้ในอีกแอป

## 3. รหัสและความปลอดภัย — ห้ามบันทึกรหัสจริงใน Repo

- ข้อความที่ผู้จัดแจ้งรหัสผ่านในบทสนทนา **เป็นความลับ**; ไม่คัดลอกรหัสลง Issue, GitHub, HTML, JS, JSON, log หรือ URL สาธารณะ
- ห้ามเก็บรหัสผ่านดิบใน localStorage, sessionStorage, IndexedDB, cookie หรือ service worker; **“จำไว้ 6 ชั่วโมง” หมายถึงจำสิทธิ์เข้าใช้งาน** ไม่ใช่จำรหัสผ่านจริง
- PIN ที่เดาได้ง่าย/ใช้ร่วมกันไม่เหมาะเป็นหลักฐานระบุตัวคนรับรอง: ใช้ได้สูงสุดเป็นตัวเปิดฟอร์มสำหรับผู้บันทึก (หลังตรวจสิทธิ์ตามนโยบาย), **ห้ามใช้ PIN อย่างเดียวอนุมัติผลเผยแพร่/แก้ผลที่รับรองแล้ว**
- รหัสจริงให้ตั้งผ่านช่องทางผู้ดูแลที่ปลอดภัยและเก็บเป็นแฮชที่ตรวจฝั่งเซิร์ฟเวอร์ (เช่น Argon2id) หรือค่าความลับเฉพาะ backend; ไม่ส่ง hash ลง frontend
- แนะนำชื่อบัญชี/สิทธิ์ต่อเจ้าหน้าที่ หากอนุญาตกรอกร่วมด้วย PIN เดียวกันต้องถือว่ายืนยันตัวผู้ทำรายการไม่ได้และบังคับผู้อนุมัติแยกต่างหาก; ไม่อ้างว่า PIN เป็นตัวพิสูจน์ “ผู้รับรอง”
- ใช้ backend ที่ตรวจ PIN + สิทธิ์ แล้วออก **เซสชันแบบเพิกถอนได้** มี `issued_at`, `expires_at` และขอบเขตสิทธิ์; ทุกการอ่านรายการภายใน/ทุกการเขียนต้องตรวจสิทธิ์และเวลาหมดอายุบนเซิร์ฟเวอร์ ไม่เชื่อแค่หน้าจอ
- แนวทางเก็บเซสชัน: พิจารณา Secure+HttpOnly+SameSite cookie ภายใต้โดเมนที่ตั้งค่าเหมาะสมก่อน; GitHub Pages → Supabase เป็นคนละ origin และ Safari/LINE อาจบล็อก cross-site cookie จึงต้องทำ QA. หากจำเป็นต้องใช้การเก็บ token ฝั่ง JS ให้ทำ threat review/XSS/CSP/TTL/เพิกถอนสิทธิ์ก่อนเปิดจริง ไม่อ้างว่าปลอดภัยเท่ากับ HttpOnly cookie
- บังคับ HTTPS, allowlist CORS ของเว็บไซต์, จำกัดจำนวนการเดารหัส/rate limit, หน่วง/พักการลองเมื่อผิดซ้ำ, CSRF protection (ถ้าใช้ cookie), ใช้สิทธิ์ขั้นต่ำและช่องทางเพิกถอนทุกเครื่อง
- ไม่เปิด direct write ไปยัง `nongkum_sports` หรือ `nongkum_published_results` จากเบราว์เซอร์ ไม่ฝัง service_role key; ตรวจ server-side authorization, payload, fixture ID, revision, duplicate และ audit
- กรณีเครื่องของกรรมการหลายคนใช้ร่วมกัน กำหนดให้กดออกก่อนส่งเครื่องต่อ; สามารถยกเลิกเซสชันจากผู้ดูแลเมื่อสูญหาย

## 4. ฟอร์มกรอกผลและลำดับการเผยแพร่

- ฟอร์มเดิมเดียวกันรองรับชนะ–แพ้, คะแนน, เซ็ต และอันดับกรีฑา; ชื่อทีม/กีฬา/รุ่นอ่านจาก fixture ที่ใช้งานจริงและล็อกไม่ให้ข้ามคู่
- ข้อมูลที่ไม่ได้รับแจ้ง เช่น คะแนน/เซ็ต ไม่สร้างขึ้นเอง; ช่องหลักฐานเลือกแนบได้ตามนโยบายกีฬา ยกเว้นรายการแก้ไขที่ผู้อนุมัติร้องขอ
- กด “บันทึกผล” = เข้าคิว **รอตรวจ** ใน `result_submissions`, แสดง “บันทึกแล้ว รอตรวจสอบ” ไม่สรุปว่าเผยแพร่แล้ว
- ผู้มีสิทธิ์รับรองตรวจข้อมูลและหลักฐาน → อนุมัติผ่านขั้นตอนฝั่งเซิร์ฟเวอร์ที่บันทึก `result_approval_audit` → เขียนเฉพาะผล approved ไป `nongkum_published_results`
- แก้ไขผลที่เผยแพร่แล้ว: เก็บรุ่นใหม่และเหตุผลแก้ไข, ไม่ overwrite ผลเดิมเงียบ ๆ; หลังรับรองจึงสลับเป็น revision ใหม่ที่หน้าเว็บอ่าน
- ถ้าผลบนหน้า “ตารางแข่งขัน” และ “ผลการแข่งขัน” ไม่ตรงกัน ให้ปิดแสดงข้อความผู้ชนะบนการ์ดที่มีข้อขัดแย้งและแจ้งทีมดูแล; ห้ามคิดผลต่างฝั่งหน้าบ้านเอง

### เงื่อนไขสำคัญก่อนเริ่ม R34-B/C
1. ผู้จัดระบุบัญชี/กลุ่มผู้มีสิทธิ์บันทึกและผู้รับรอง **แยกจากกัน**; หากจะใช้รหัสร่วม ต้องจำกัดสิทธิ์ไม่ให้เผยแพร่ผลเอง
2. เลือกกลไกเซสชันที่ใช้งานจริงบน Safari/Chrome/LINE ก่อนสัญญาว่า “จำได้ 6 ชั่วโมง” ทุกสภาพแวดล้อม
3. รหัสจริงต้องตั้งนอก repo ผ่านช่องทางปลอดภัย และควรเปลี่ยนรหัสที่พูดออกเสียงไว้แล้ว
4. ทดสอบข้อมูลผลปลอมเฉพาะสภาพแวดล้อมทดสอบ ไม่ปะปนกับผลกีฬาจริง

## 6. ผลกระทบและสิ่งที่ไม่แตะรอบแผน
- **ไฟล์คาดว่าแตะเมื่อ implement:** `index.html`, `js/program.js`, `results.html`, `js/results.js`, `js/results-renderers.js`, CSS การ์ด, JS การเข้าใช้งาน/ฟอร์มแยกใหม่, Supabase migrations/Edge Functions; ต้องเช็คสาขาคู่ขนานก่อนเริ่ม
- **ไม่แก้ในรอบนี้:** รหัสผ่านจริง, Supabase rows, ข้อมูลโปรแกรม/ผลจริง, `data/public-results.json`, คำสั่ง/ประกาศ/สูจิบัตร, หน้าเว็บที่เผยแพร่, Google Sheets; ไม่มีการ merge หรือ deploy
- ข้อเสนอเริ่มจากความต้องการสะดวก 6 ชั่วโมง แต่ไม่ลดการตรวจรับ/สิทธิ์/ประวัติผลที่เผยแพร่จริง
