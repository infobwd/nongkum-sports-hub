# อัปเดตข้อกำหนด R43-F — PIN รายบุคคลผูกกับรายชื่อเจ้าหน้าที่ (17 พ.ย. 2569)

**คำชี้แจงล่าสุดของผู้จัดแทนแนวทาง Supabase Auth + PIN ส่วนกลางที่เคยเสนอไว้ด้านล่าง**: ไม่ต้องเชื่อม LINE ไม่ต้องให้กรอกอีเมล ไม่ต้องให้เจ้าหน้าที่เลือกชื่อตนเองจากหน้าจอเพื่ออ้างสิทธิ์ ผู้ใช้แต่ละคนใช้ PIN ของตนเอง และระบบฝั่งเซิร์ฟเวอร์จับคู่ PIN กับ **ระเบียนบุคคลที่ผู้จัดอนุญาต** เพื่อทราบชื่อ โรงเรียน และบทบาทว่าเป็นผู้บันทึก/ผู้เสนอ หรือผู้ตรวจ/ผู้รับรองโดยอัตโนมัติ

## สถาปัตยกรรมที่ต้องออกแบบและทดสอบใหม่
1. จัดทำทะเบียนผู้ใช้งานส่วนตัวเฉพาะผู้ที่ผู้จัดอนุมัติ โดยมีตัวระบุถาวร (UUID), ชื่อจริงจากบัญชีรายชื่อกรรมการ, สังกัด, บทบาทเสนอ/จัดกรรมการ/ตรวจรับรอง และสถานะเปิด/ปิด; ไม่คัดลอกทะเบียนเจ้าหน้าที่ฉบับร่าง 8 รายชื่อให้มีสิทธิ์โดยอัตโนมัติ
2. ใช้ PIN ที่ออก **แยกให้แต่ละบุคคล** (ห้ามใช้ PIN ส่วนกลางเป็นตัวบ่งชี้ชื่อ) ตรวจรหัสเฉพาะเซิร์ฟเวอร์; เก็บรหัสแบบ hash ที่เหมาะสมกับความลับความยาวสั้น ไม่เก็บ plaintext ในฐานข้อมูลหรือ GitHub และไม่ใช้ชื่อที่กรอกเองเป็นหลักฐานตัวตน
3. การล็อกอินสร้าง session แบบสุ่มอายุไม่เกิน 6 ชั่วโมง ผูกกับรหัสบัญชีและบทบาท, เก็บ hash session ฝั่งเซิร์ฟเวอร์, เพิกถอนและเปลี่ยนรหัสได้; จำกัดความถี่การเดารหัสและมีขั้นตอนออก/รีเซ็ตรหัสอย่างปลอดภัย
4. หน้าจอเจ้าหน้าที่ให้ **กรอกรหัสของตนเองช่องเดียว** แล้วแสดงชื่อ สังกัด และหน้าที่ที่ผูกไว้ โดยไม่เปิดเผยว่ารหัสของบุคคลใดถูกต้องแก่ผู้ที่ยังไม่ผ่านการตรวจ
5. แก้ R43 gateway และ role mapping ให้ใช้ตัวตนที่ยืนยันจาก session ฝั่งเซิร์ฟเวอร์ แทนการพึ่งอีเมล/Supabase Auth UI; ขณะนี้ฐานจริงมี r43_roles.user_id อ้างอิง auth.users และ PR #170 ตรวจ Auth JWT ทุกคำขอ **จึงยังนำโค้ดเดิมไปใช้งานตามข้อกำหนดใหม่ไม่ได้** ต้องออกแบบ migration แบบรักษา schema และ audit เดิมให้ปลอดภัยก่อน
6. ยังคงแยกสิทธิ์ผู้เสนอและผู้ตรวจ, ห้ามรับรองคำขอของตนเอง, เก็บ actor UUID ในประวัติ, ไม่ยกระดับสิทธิ์จากการรู้รหัสกลางหรือระบุชื่อเอง, ไม่อนุมัติเท่ากับเผยแพร่
7. ปรับเฉพาะ R43 ก่อน ตรวจผลกระทบต่อ R34/R37 โดยยัง **ไม่แก้ระบบบันทึกผลแข่งที่ใช้จริง**; หากจะรวมรหัสของบุคคลเดียวให้ใช้ได้ทั้งงานผลแข่งขันและจัดตาราง ต้องจัดการ migration บทบาท/เซสชันแยกเป็นขั้นต่อไป
8. ทดสอบ PIN คนละคน, รหัสผิดและเดาถี่, session หมดอายุ/ถูกยกเลิก, ผิดบทบาท, รับรองตนเอง, การบันทึก audit, มือถือ Safari/Chrome/LINE และคงข้อมูล R32/R33 ก่อนขอ Merge

## สถานะ
- ยืนยันจากผู้จัด: **ผู้ตรวจ R43 คือ นายนพรุจ ลับบัวงาม** ตามสูจิบัตร (ตัวบุคคลยืนยันแล้ว ไม่ใช่การเปิดสิทธิ์)
- รหัสรายบุคคลยังไม่ได้ออก, ยังไม่ได้ผูกตัวตนหรือมอบสิทธิ์, ยังไม่แก้โค้ด PIN รายบุคคล, ยังไม่ได้ติดตั้งฐานหรือเผยแพร่
- **PR #170 ต้องถือเป็น Draft ระหว่างปรับโค้ดใหม่**; ผลทดสอบของสถาปัตยกรรมเก่าไม่ใช่หลักฐานว่ารูปแบบ PIN รายบุคคลผ่านแล้ว
- เก็บแผนเดิมต่อท้ายเพื่อรักษาประวัติและเป็นข้อมูลว่าต้องปรับส่วนใด ไม่ให้ Merge ตามแผนเก่า

# บันทึกแผนก่อนเปลี่ยนข้อกำหนด (เก็บเพื่อประวัติ)

# R43-F — ใช้รหัสผลแข่งขันเดิมกับการจัดตาราง (17 พ.ย. 2569)

## คำขอและขอบเขต
ผู้จัดต้องการใช้รหัสผู้บันทึกผล R34 สำหรับเสนอแก้ตาราง/กรรมการ และรหัสผู้ตรวจผล R37 สำหรับตรวจคำขอ R43 โดยไม่สร้างรหัสกลางชุดใหม่; ยึดบัญชีรายบุคคลเพื่อระบุผู้กระทำจริง

## หลักฐานต้นทาง
- PR #168/#169 Merge แล้ว; R43 มีตารางส่วนตัว 7 ตาราง/RLS และ r43_roles ยังไม่มีสมาชิก
- R34/R37 ใช้ session หกชั่วโมงในฐาน editor_sessions/reviewer_sessions พร้อม hash ของ token และ revoke ได้
- R43 มี Supabase Auth/JWT เพื่อระบุตัวตน และ SQL gateway จำกัดผู้เสนอ/ผู้รับรอง แยกกัน; Edge nongkum-schedule-admin ยังไม่ deploy และไฟล์เปิดใช้งานฝั่งสาธารณะยังไม่พร้อม
- PR เปิดเดิม #144 (R33) และ #159 (กิจกรรมภาพ): หลีกเลี่ยงแก้โค้ดเดิม R34/R37 และข้อมูลผล R32

## แบบที่อนุมัติให้พัฒนา
1. ใช้บัญชี Supabase Auth รายบุคคลครั้งแรก/เมื่อหมดอายุเพื่อระบุผู้ปฏิบัติ ไม่ใช่เอา shared PIN มาแทนบุคคล
2. ใช้ token R34 เดิมเพื่อเปิดงานเสนอและมอบหมาย; token R37 เดิมเพื่อเปิดคิวตรวจ/รับรอง; ถ้าปลดล็อก R34/R37 ในเครื่องแล้ว ให้ใช้ session เดิมได้ภายใน 6 ชั่วโมง ไม่เก็บ PIN
3. R43 Edge ตรวจ JWT จาก Auth ทุกคำขอ แล้วตรวจ token PIN เดิมแบบ hash กับตาราง session ที่ยังไม่หมดอายุ/ไม่ revoke จากฝั่ง service role; ไม่ส่ง token เข้า R43 gateway/audit
4. ต้องผ่าน R43 role allowlist เพิ่มเติม: can_propose/can_assign/can_review; ผู้เสนอรับรองงานตัวเองไม่ได้ (แม้มีทั้งสอง PIN)
5. ถ้าขาด Auth, สิทธิ์, token เดิม, config หรือ Edge ให้ปิดการเข้าถึง ไม่เปิด public write และไม่เผยแพร่ตาราง
6. จำกัด CORS, body size, แยก PIN role ต่อ action, ไม่ฝัง secret ลงหน้าเว็บ; การออกจาก R43 ไม่ revoke session ของ R34/R37 ที่ใช้กับหน้าผลแข่งอยู่แล้ว

## ผู้ตรวจ R43-F ที่ผู้จัดยืนยัน (17 พ.ย. 2569)
- **ยืนยันตัวบุคคลตามสูจิบัตร**: ผู้จัดยืนยันว่าผู้ตรวจคือ **นายนพรุจ ลับบัวงาม** ผู้อำนวยการโรงเรียนบ้านวังด้ง ตรงกับรายการคณะกรรมการฝ่ายบันทึกผลการแข่งขันกีฬาและกรีฑา ฉบับร่าง section 11 ลำดับ 11.1 หน้า 10
- คำถอดเสียงในบทสนทนาก่อนหน้า (“นพรุษ ละบวงาม” และ “นพรุษ ลับบัวงาม”) ให้ถือเป็นการสะกดคลาดเคลื่อน **ไม่ใช่บุคคลเพิ่มเติม**; ใช้ชื่อ **นายนพรุจ ลับบัวงาม** เป็นชื่ออ้างอิงของผู้ตรวจที่ผู้จัดระบุ
- **สถานะที่ยืนยัน**: ชื่อบุคคลสำหรับหน้าที่ผู้ตรวจได้รับการยืนยันจากผู้จัดแล้ว แต่ **ยังไม่เท่ากับการยืนยันบัญชี Supabase Auth หรือมอบสิทธิ์ R43**
- ยังไม่มี Auth UUID ที่ตรวจยืนยันว่าเป็นบัญชีของท่าน; ห้ามจับคู่บัญชีจากชื่อ/อีเมลที่เดา และห้ามยกระดับสิทธิ์โดยอาศัยรหัส PIN ผู้ตรวจที่ใช้ร่วมกันเพียงอย่างเดียว
- ขั้นต่อไป: ตรวจหลักฐานและบัญชี Supabase Auth รายบุคคลของท่านอย่างเป็นส่วนตัว → ผูก UUID ของบัญชีที่ยืนยันกับ `can_review` → ตรวจว่าผู้เสนอและผู้รับรองเป็นคนละคน → ทดสอบ reviewer PIN + Auth กับข้อมูลจำลอง ก่อนเปิดใช้งานจริง
- **สถานะงาน**: ยืนยันชื่อผู้ตรวจแล้ว / รอพิสูจน์บัญชีและมอบสิทธิ์จริง / PR #170 ยังรอ Merge และยังไม่เปิด R43 production
