## 1. เป้าหมายและเงื่อนไขหลัก

ทำให้สูจิบัตร V4.2 อ่านง่ายสวยงามแบบ **นิตยสารกีฬา** โดย **ไม่แลกกับความครบถ้วนของข้อมูล**:

1. หน้าประกาศ/คำสั่งดูทางการและ **ครบความเหมือนต้นฉบับ** ไม่ตัดรายละเอียดเพื่อให้หน้าดูโล่ง

4. การ์ด Match Day ใช้สีประจำโรงเรียนจากข้อมูลที่ตรวจสอบได้ พร้อมรูปแบบขาวดำที่ยังอ่านออก
5. สร้างผังสาย/การประกบคู่ใหม่จาก \`fixture.id\` และลิงก์รอบที่ตรวจสอบจริง ค่อยลดหน้า PDF V3 ที่นำมาต่อท้าย เมื่อเทียบเนื้อหาทุกส่วนแล้วว่าไม่ตกหล่น

**ไม่ใช่ภารกิจนี้:** ประกาศคำสั่งจริง, อนุมัติวัน/เวลาใหม่, ตรวจพบเด็กชนกันจากข้อมูลสาธารณะ, สร้างผลการแข่งขัน, แก้ต้นฉบับ Docs หรือเปลี่ยนเว็บทันที

## 3. งาน A — ความครบถ้วนของประกาศ/คำสั่ง (ลำดับแรก)

**ข้อบกพร่อง V4.1 ที่พบ:** \`notice()\` ใน \`scripts/docs/v41_editorial.py\` ดึงเพียงช่วงต้นของ V3 หน้า 6 และส่วนท้ายหน้า 16 เพื่อจัดประกาศ จึงไม่มีหลักประกันว่าเนื้อหาช่วงหน้า 7–15 ครบในข้อความหน้าเอกสาร ถึงแม้มีทะเบียนกรรมการแสดงต่ออีกหมวด

**แนวทาง V4.2:**
- ถอดโครงสร้างจากต้นฉบับเป็น \`preamble\`, \`legal_basis_if_present\`, \`sections[]\`, \`duties[]\`, \`effectiveness_if_present\`, \`closing\`, \`signature_placeholder\` โดยชี้หน้า/ข้อความต้นทางทุกย่อหน้า
- ใช้การจัดหน้าทางการ **Sarabun (Google Fonts, ไทยมีหัว)** ต่อจาก V4.1; TH Sarabun New เป็นทางเลือกเมื่อมีไฟล์/สิทธิ์เหมาะสม ไม่เปลี่ยนฟอนต์โดยพลการ
- แยก **ข้อความประกาศ/คำสั่ง** ออกจาก **ทะเบียนคณะกรรมการ** แต่มีการอ้างถึงข้อ/หมวดตรงกัน และไม่ลบบทบาท/หน้าที่ที่กำหนดไว้ในต้นฉบับ
- ถ้าในต้นฉบับใช้ทั้งคำว่า “ประกาศ” และ “สั่ง ณ วันที่” ให้ทำรายการ unresolved **ไม่ตัดสินประเภทเอกสารเอง**; ไม่แต่งเลขที่ วันลงนาม ข้อกฎหมาย ชื่อผู้ลงนาม หรือลายเซ็น
- ทำ side-by-side audit โดยนับย่อหน้า/หมวด/ข้อ/รายการที่ map ได้และรายการที่ขาด; **ห้ามใช้การตัดข้อความให้พอดีหน้ากระดาษเป็นวิธีแก้ overflow**
- จัด typography ให้ราชการโดยใช้หัวกระดาษ ลำดับข้อ เยื้องย่อหน้า ช่องว่างลงนาม ความคงที่ของฟอนต์/ตัวเลข และลายน้ำ “ร่าง”

**ผ่านเมื่อ:** ตรวจครบทุกข้อความสาระสำคัญและหมวดจากต้นฉบับ; หากยังขาดรายการ ให้ล็อกเป็น review blocker ไม่สร้างหน้าทางการปลอมที่ดูเหมือนออกคำสั่งแล้ว

- คำปฏิญาณคงเป็นหน้า editorial quote แยก หรือจัดในส่วนพิธีตามโครงจริง; เทียบคำต่อคำกับต้นฉบับก่อนเรียกว่าผ่าน

**ผ่านเมื่อ:** เวลา/ข้อความ/ลำดับเทียบ V3 ได้ครบ, อ่านรายละเอียด 08.45 ได้โดยไม่ต้องอ่านข้อความก้อนยาว, ไม่มีเหตุการณ์หรือเวลาสมมติ

## 5. งาน C — หลักเกณฑ์การแข่งขันแบบ modern rules

**ปัญหา V4.1:** \`build-v4-full.py\` ใช้ \`excerpt(pdf,17)\` ทำให้ส่วนกติกายังเป็นข้อความถอดจาก PDF ที่จัดรูปแบบไม่ดี

**แนวทาง V4.2:**
- ทำ \`rules-model\` รายข้อพร้อม \`rule_id\`, \`source_page\`, \`source_excerpt\`, \`approved_status\`, \`sport_scope\` และ \`display_type\`
- แยก **คะแนนรวมถ้วยรางวัล** ออกจาก **กติกาคิดผลของแต่ละกีฬา**: ฟุตบอล/ฟุตซอล, เปตองแพ้คัดออก, กรีฑา, และกีฬาที่เหลือตามหลักฐาน
- ใช้การ์ดตัวเลข ตารางอันดับ flow ขั้นตอน และกรอบ “กรณีคะแนนเท่ากัน” โดยไม่ซ่อนคำจำกัดความและลำดับเกณฑ์รอง
- ตัวอย่าง **ฟุตบอล** ใช้ชนะ 3/เสมอ 1/แพ้ 0 ตามผู้จัดเคยยืนยัน และหัวข้อ head-to-head/ใบเหลือง–แดงตามหลักฐานที่ต้องทวนลำดับบังคับจริง; ไม่เติมลำดับตัดสินที่ยังไม่มีหลักฐาน
- แสดง “ยังรอรับรอง” เฉพาะกติกาที่ยังไม่ชัด ไม่สื่อว่าทั้งชุดได้รับการอนุมัติแล้ว
- หน้า infographic ต้องพิมพ์ A4 ขาวดำชัด และมีภาคข้อความกติกาฉบับเต็มหรืออ้างอิงครบ

**ผ่านเมื่อ:** ทุกเกณฑ์สำคัญมีหลักฐานและเทียบข้อความได้; infographic ไม่ขัด/ไม่ลดรายละเอียดกติกาที่ใช้แข่งขันจริง

## 6. งาน D — Match Day พร้อมสีประจำโรงเรียน

**ปัญหา V4.1:** \`sports_cards()\` ให้การ์ดคู่สวยขึ้นแล้ว แต่ยังไม่มีสีทีม และตอนนี้ \`COLORS\` ในโมดูล editorial เป็น **สีประมาณ** ไม่ใช่รหัสสีประจำโรงเรียนที่รับรอง

**แนวทาง V4.2:**
- สร้าง school palette map แยกจาก renderer, key ด้วย school ID/alias ที่ผูกกับ \`data/program...json\` และ V3 หน้า 5 — ไม่จับคู่ด้วย substring ของชื่ออย่างเดียว
- นำสีจริง/ชื่อสีที่โรงเรียนยืนยันมาเป็น swatch คู่แข่งขันซ้าย–ขวา; ถ้าสี hex ยังไม่รับรอง ให้ใช้ชื่อสีจากหลักฐานและโทนที่ติดป้าย “สีประกอบ” หรือใช้สีเทากลาง
- ใช้ card แบบ VS พร้อมเส้นคั่น/แถบสีสองทีม, ระดับรุ่น, วันเวลา, รอบ, สนาม, สถานะยืนยันและ source fixture ID ในชั้นข้อมูล
- คู่ที่ยังไม่ทราบทีมใช้ “รอผลคู่ที่ …” หรือ “รอประกบ” ตามข้อความต้นทาง ไม่ตกแต่งเป็นทีมใหม่
- ทดสอบพิมพ์ขาวดำ, contrast, ความยาวชื่อไทย, สีคู่ที่คล้ายกัน และการอ่านบนมือถือ/แท็บเล็ต
- ไม่เปลี่ยนตารางหลักแบบเป็นระเบียบให้กลายเป็นการ์ดทั้งหมด; ใช้การ์ดเฉพาะหน้าคู่เด่น/เปิดหมวดเพื่อรักษาความหนาแน่นข้อมูล

**ผ่านเมื่อ:** สีไม่ผูกผิดโรงเรียน, ตารางมีข้อมูลครบเดิม, ไม่มีคู่สมมติ, มองแยกคู่ได้แม้พิมพ์ขาวดำ

## 7. งาน E — วาดผังสายใหม่แทนหน้า V3 เดิม (ต้องตรวจข้อมูลก่อน)

**ปัญหา V4.1:** \`build-v4-full.py\` ยัง append หน้าจริง V3 จำนวน **17 หน้า** จาก \`original_appendix\`. ลักษณะภาพ/ตัวอักษรจึงไม่เป็นงานออกแบบเดียวกัน และบางข้อมูลเก่าอาจขัดกับ corrected program

**แบบผังที่อนุญาต:**
1. **พบกันหมด/ลีก:** ตารางจับคู่และตารางอันดับ ไม่แสดงลูกศรคัดออก
2. **แพ้คัดออก:** bracket แบบเชื่อมคู่ต่อคู่ เฉพาะเมื่อมี \`match_id\`, \`round\`, \`winner_to_match_id\` หรือหลักฐานอ้างอิงที่ตรวจได้
3. **กลุ่ม + รอบสุดท้าย:** วาดสองส่วน โดยรอบที่ยังไม่ทราบคู่แสดง \`รออันดับกลุ่ม/รอผลคู่\`
4. **รายการกรีฑา/ช่องลู่:** ใช้ตารางแบ่งฮีต/ลู่ ไม่วาด bracket โดยไม่มีเหตุผล
5. **ผังสายจากภาพที่ถอดไม่ครบ:** คงหน้าภาคผนวกเดิมเฉพาะส่วน พร้อมป้าย “ร่างอ้างอิง” ไม่สร้างภาพใหม่ด้วยการเดา

**ขั้นตอนทำ:** inventory 17 หน้าเดิม -> บันทึกทุกคู่/ทีม/รอบ/สาย/กติกา/แหล่งที่มา -> mapping กับ stable fixture IDs -> สร้าง bracket JSON ที่ผ่าน validation -> render เป็น SVG/vector ใน PDF -> เทียบหน้าต่อหน้า -> เอา original V3 appendix ออก **เฉพาะหน้าที่แทนได้ครบและยืนยันแล้ว**. รายการที่ยังไม่มั่นใจไม่ถอดออก

**ผ่านเมื่อ:** ไม่มีทีม/คู่/รอบตกหล่นและไม่มีเส้นเชื่อมผิด; สถานะ “รอ...” ชัด; ไม่เปิดตัว PDF ที่ตัดภาคผนวกทั้ง 17 หน้าโดยยังไม่มีหลักฐานเทียบครบ
