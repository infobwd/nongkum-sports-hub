# มิตรภาพเกม 2569 — แนวทางแสดงโปรแกรมและผลการแข่งขัน (Results v1)

สถานะ: **DESIGN / ยังไม่มีผลการแข่งขันที่รับรอง / ไม่เผยแพร่คะแนนสมมติ**  
แหล่งข้อมูลชื่อการแข่งขัน: ข้อความผู้ประสานงานวันที่ 4 พฤศจิกายน 2569 — ใช้คำว่า **“มิตรภาพเกม”** ตามที่แจ้ง ไม่แก้การสะกดเอง

## 1. สรุปหน้าจอมือถือที่ตรวจพบ

- ส่วนหัวเรียบร้อย แต่ Safari iPhone มีช่องว่างด้านบน และโลโก้ถูกบังเมื่อเลื่อน: CSS เดิมบังคับ fixed mask ขั้นต่ำ 44px แม้ safe inset จริงเป็น 0; เอาการบังคับขั้นต่ำออกแล้วใน PR นี้ เพื่อให้ browser จัดการ native chrome ตามปกติ (ยังต้องตรวจบนเครื่องจริง)
- การ์ดฟุตบอลบนภาพปัจจุบันอ่านง่าย มีคู่แข่งขันและเวลาใน PDF; แต่ข้อความ “วันรอยืนยัน” ถูกจัดรวมกับข้อมูลทุกประเภทรวมกัน
- ข้อมูลที่ยืนยันเฉพาะสนาม/วัน ต้องแสดงต่างจากข้อมูลที่ยังไม่รับรอง และไม่ยกระดับ `review` ทั้งแถวเป็น `approved` จนผ่านเกณฑ์ P2
- UI ควรเพิ่มหน้า/โหมด “ผลการแข่งขัน” ภายหลัง โดยไม่แทรกคะแนนสมมติลงบนการ์ดทุกใบในตอนนี้

## 2. แสดงข้อมูลตามสถานะแต่ละฟิลด์

| ข้อมูล | กีฬาทั่วไปที่ยังไม่รับรอง | เปตองนอกรอบ 24 คู่ | ข้อควรระวัง |
|---|---|---|---|
| วันแข่งขัน | วันรอยืนยัน | **12 พ.ย. (10 ปี), 13 พ.ย. (12 ปี)** — ยืนยัน | ยืนยันเฉพาะคู่รอบแรก/รองชนะเลิศ |
| สถานที่ | ถ้า PDF ระบุหมายเลขสนามให้แสดงว่า “ตาม PDF” | **โรงเรียนบ้านหนองกระทุ่ม** — ยืนยัน | สถานที่ไม่เท่ากับหมายเลขคอร์ต/สนามย่อย |
| เวลา | เวลาใน PDF ถ้ามี หรือรอยืนยัน | **เวลาแข่งรอแจ้ง** | ไม่ประมาณช่วงเวลาเอง |
| รอบแข่งขัน | ตาม PDF | รอบแรก/รองชนะเลิศตาม PDF | ผังเปตอง 10 ปีชายมี QA-06 ค้างอยู่ |
| รายการทั้งแถว | ข้อมูลร่าง | **Review** ยังไม่ผ่านอนุมัติรายคู่ | ไม่ประกาศผลหรือคะแนน |

สถานะ `draft` ในข้อมูล PDF, `review` ใน Google Sheets และยืนยันบางฟิลด์เป็นคนละระดับความหมาย ต้องแยกชัดใน UI

## 3. ออกแบบ UX สำหรับผลการแข่งขันในอนาคต

หลังจากมีข้อมูลจริงที่กรรมการรับรองแล้ว ให้มีสองมุมมอง **“โปรแกรมการแข่งขัน”** และ **“ผลการแข่งขัน”** โดยใช้ตัวเลือกโรงเรียน/กีฬา/ช่วงชั้นชุดเดียวกัน

### 3.1 การ์ดโปรแกรมการแข่งขัน

- กีฬา · รุ่นอายุ · เพศ · คู่ที่/รายการที่
- ทีม A — ทีม B (หรือชื่อรายการและลู่กรีฑา)
- วัน เวลา สนาม แต่ละฟิลด์แสดงสถานะ “ยืนยันแล้ว / ตาม PDF / รอตรวจ”
- ปุ่มดูรายละเอียด ข้อมูลต้นฉบับ และ QA; แสดงที่มาอย่างกระชับ

### 3.2 การ์ดผลแข่งขัน (จะแสดงต่อเมื่ออนุมัติผลจริงเท่านั้น)

- **กีฬาประเภทพบกัน:** ชื่อทีม 2 ฝั่ง คะแนนแต่ละฝั่ง สถานะจบการแข่งขัน และผู้ชนะหรือผลเสมอ (ถ้ากติกาอนุญาต)
- **กรีฑา/ประเภทเรียงลำดับ:** ชื่อรายการ รุ่น เพศ อันดับ 1–3 พร้อมโรงเรียน และสถิติ/เวลาเมื่อมีข้อมูลจริง
- **สถานะผล:** `awaiting_result` (ยังไม่รายงาน), `draft` (กรรมการกำลังบันทึก), `review` (รอตรวจ), `approved` (แสดงในเว็บได้), `corrected` (แก้ไขผลหลังอนุมัติพร้อมหลักฐาน)
- ถ้าผู้ใช้เลือกแท็บผลขณะยังไม่มีผล approved: ข้อความ **“ยังไม่มีผลการแข่งขันที่ผ่านการรับรอง”** เท่านั้น
- ไม่แสดงชื่อ/เลขประจำตัว/วันเกิดเด็กในเว็บสาธารณะ
- ถ้าจำเป็นต้องแสดงคะแนนรวมโรงเรียน ต้องยืนยันวิธีนับ 5–3–2, กติกากรณีเสมอ/ยกเลิก/มีหลายทีม ก่อนคำนวณและเผยแพร่

## 4. ข้อมูลสำหรับผู้จัดใน Google Sheets (P3 Results)

เสนอ **เพิ่มแท็บ `07_ผลการแข่งขัน`** ภายหลัง โดยไม่ปะปนกับ `04_คู่แข่งขัน` และ `05_กรีฑา` ซึ่งเป็นข้อมูลโปรแกรม

คอลัมน์หลักที่เสนอ:
`result_id`, `fixture_id`, `sport_id`, `result_type`, `team_a_score`, `team_b_score`, `winner_school_id`, `rankings_json` (เฉพาะกรีฑา/จัดอันดับ), `recorded_at`, `result_status`, `reviewer`, `approved_at`, `evidence_link`, `revision`, `reason`.

หลักการ:
1. อ้างอิง `fixture_id` จาก P1 เป็น **ID หลัก** ไม่อิงเลขคู่ที่อาจซ้ำตาม PDF
2. ผลอาจเริ่มเป็น Draft แล้วถูกแก้ระหว่างการตรวจ ไม่ให้เว็บอ่านผล Draft หรือ Review ตรงจาก Sheet
3. ผู้รับรองใช้สิทธิ์ใน P2/P3 และต้องมี audit trail; แก้ผลหลังประกาศต้องมี revision และเหตุผล
4. สร้าง approved-only snapshot แบบสาธารณะโดยตัดอีเมลผู้รับรองและข้อมูลส่วนบุคคลออก
5. ใน GitHub Pages ให้แสดงผลเฉพาะ `approved` พร้อมเวลาอัปเดตและหมายเหตุ “ผลรับรอง”; ถ้าค่าขาดหรือขัดแย้งให้ไม่เผยแพร่
6. เริ่มใช้การ์ดผลในเว็บไซต์เมื่อทดสอบการนำเข้าและการอนุมัติจริงแล้วเท่านั้น

**ยังไม่สร้างแท็บ/ไม่ใส่ผลการแข่งขันจริงในงานนี้** เพราะยังไม่ได้รับคะแนนหรือผลที่กรรมการลงนามรับรอง

## 5. สิ่งที่ยังต้องตรวจหรือยืนยันก่อนเปิดแสดงผล

- [ ] ผังเปตอง 10 ปีชาย (QA-06)
- [ ] ปรับชื่อแสดงผลเป็น “มิตรภาพเกม” ตามคำแก้ไขของผู้จัด พร้อมตรวจอัตลักษณ์ป้ายจริงอีกครั้ง
- [ ] ผู้บันทึกผล ผู้ตรวจผล และผู้อนุมัติผล: บัญชี/บทบาท แยกกัน
- [ ] กติกาคิดคะแนนรวมและวิธีแสดงอันดับ

## 6. การเปลี่ยนแปลงที่ทำทันทีในรอบนี้

- เปลี่ยนชื่อแสดงบนเว็บเป็น **มิตรภาพเกม** ตามข้อความที่ได้รับ
- แสดงวันและสถานที่เปตองนอกรอบเป็น **ยืนยันแล้ว**; เวลาเป็น **รอแจ้ง**
- สถานะรวมคู่เปตองยังเป็น `review` ใน Sheet และยังเป็น `draft` ในข้อมูล PDF ต้นฉบับ
- แก้ CSS fixed mask บน Safari ที่เคยบังคับ 44px แม้ safe inset ไม่ต้องการ
- ไม่เปลี่ยนข้อมูลคู่แข่ง สถิติ ผลการแข่งขัน หรือวันแข่งของรายการอื่น

## บันทึก R1–R3

ชื่อการแข่งขันแก้เป็น **มิตรภาพเกม** ตามผู้จัด และได้แยก `results.html` จาก `index.html`; ดู [ขั้นตอนการทำจริง](RESULTS_IMPLEMENTATION_R1_R3.md). ข้อมูลผลการแข่งขันยังไม่มีรายการ Approved จึงแสดงสถานะว่าง ไม่สร้างผลสมมติ
