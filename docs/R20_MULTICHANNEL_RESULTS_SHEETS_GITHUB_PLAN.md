# R20 — แผนรับ–บันทึก–ตรวจรับผลการแข่งขันแบบหลายช่องทาง (มิตรภาพเกมส์ 2569)

**วันที่บันทึกแผน:** 6 พฤศจิกายน 2569  
**สถานะ:** DESIGN / PLAN ONLY — ยังไม่ได้พัฒนาหน้ากรอกผล เชื่อมบริการเขียน Google Sheets หรือตั้งส่งผลไป GitHub อัตโนมัติ  
**หลักการ:** ใช้เว็บไซต์เดิมเป็นหลัก, Google Sheets เป็นฐานข้อมูลการทำงานกลาง, เผยแพร่เฉพาะผลที่ผู้มีสิทธิ์รับรอง, คงวิธีถ่ายรูปส่ง ChatGPT ที่เคยใช้ได้  
**สำหรับผู้ใช้ทั่วไป:** ภาษาธรรมดา อ่านเข้าใจทันที ไม่บังคับให้รู้ศัพท์ระบบคอมพิวเตอร์

## 1. ตรวจสถานะระบบเดิมก่อนพัฒนา

- เว็บไซต์ GitHub Pages ปัจจุบันมี `index.html` (ตารางแข่งขัน), `results.html` (ผลที่ผ่านรับรอง), `standings.html` (อันดับ), และ `forms/score-sheet.html` (ใบบันทึกผล A4 แบบไม่เขียนกลับฐานข้อมูล)
- `js/results.js` อ่าน `data/public-results.json` เฉพาะผลที่ `approved` และรีเฟรชข้อมูลได้; ปัจจุบันชุดสาธารณะยังมีผลรับรอง 0 รายการ
- Google Sheets มีแท็บ `07_ผลประเภททีมคู่` และ `08_ผลกรีฑา` ที่ยังไม่มีผลจริง; `apps-script/Code.gs` และ `apps-script/Results.gs` มีตัวอย่างการตรวจสิทธิ์ รับรอง และส่งออกไฟล์ส่วนตัว แต่ **ยังไม่ยืนยันว่าติดตั้ง/ใช้งานจริงใน Google Sheets**
- โปรแกรมการแข่งขันล่าสุดใน repo มี 187 คู่ + 50 รายการกรีฑา แต่แท็บ `04_คู่แข่งขัน` ใน Sheets มี 186 คู่; รายการฟุตบอลมัธยมหญิงที่เพิ่มใน repo ยังต้องตรวจว่าซ้ำหรือเป็นคู่จริง
- วัน/เวลา/สนามที่รับรองใน repo มีความต่างจาก Sheets; ต้อง reconcile เฉพาะค่าที่มีหลักฐานยืนยันจริงก่อนเปิดการกรอกผลหรือเชื่อมการเผยแพร่ ไม่เดาข้อมูลเพื่อให้จำนวนตรงกัน
- เอกสารอ้างอิงที่ต้องคงไว้: `docs/RESULTS_IMPLEMENTATION_R1_R3.md`, `docs/R15_RESULTS_STANDINGS_PHOTO_JSON_PLAN.md`, `docs/P2_SHEETS_WORKFLOW.md`.

## 2. ช่องทางรับผลทั้งสามแบบ — ไม่ยกเลิกของเดิม

1. **ช่องทาง A: บันทึกผ่านเว็บไซต์** — กรรมการเปิดรายการแข่งขันจากหน้าเดิม กด “บันทึกผล” กรอกตามชนิดกีฬา; ระบบตรวจสิทธิ์แล้วบันทึกผลรอตรวจใน Google Sheets ผ่านบริการกลางที่ปลอดภัย ไม่ฝังกุญแจเขียนชีตไว้ในหน้า GitHub Pages
2. **ช่องทาง B: ถ่ายภาพส่งใน ChatGPT** — ผู้ดูแลส่งภาพใบบันทึกผลให้ AI ช่วยอ่านข้อความ ผูกคู่แข่งขัน และหาจุดผิดสังเกต; ผู้รับผิดชอบต้องตรวจรับก่อนเผยแพร่; คงการสร้าง/แก้ `data/public-results.json` ผ่าน PR เป็น fallback ช่วงเปลี่ยนผ่าน และเมื่อ Sheets เป็นแหล่งหลักแล้วให้นำผลผ่านคิวตรวจ Sheets ก่อนส่งออก JSON เพื่อไม่ให้ข้อมูลสองแห่งขัดกัน
3. **ช่องทาง C: บันทึกใน Google Sheets โดยตรง** — เจ้าหน้าที่กรอกในแท็บผลเดิม ใช้เมนูตรวจ/รับรองที่ควบคุมสิทธิ์; Apps Script รวบรวมเฉพาะผลที่รับรองแล้ว สร้าง JSON รุ่นใหม่ และส่งไป branch/PR ใน GitHub เพื่อผ่าน CI + ผู้รับผิดชอบตรวจ Merge ก่อนเผยแพร่

**แหล่งข้อมูลจริง:** Google Sheets เป็น *working source of truth* เมื่อระบบเชื่อมพร้อมใช้งาน; `data/public-results.json` เป็น *published approved-only snapshot* ของเว็บไซต์ ไม่ใช่ฐานข้อมูลกรอกแข่งแยกอีกแห่ง; `standings.html` ต้องใช้อันดับที่คำนวณจากผลรับรองเดียวกัน.

## 3. ภาพหลักฐาน: ไม่บังคับทุกชนิดกีฬา

- ผลแข่งขันปกติทุกกีฬา: ช่อง “แนบภาพใบบันทึกผล (ถ้ามี)” เป็น **ทางเลือก**; บันทึกผลได้หากผ่านการตรวจช่องสำคัญและสิทธิ์
- ข้อมูลไม่ตรงกัน, อ่านผลไม่ชัด, ข้อโต้แย้ง, แก้ผลหลังรับรอง: ให้ผู้ตรวจพิจารณา/ร้องขอหลักฐานเพิ่มเติม และอาจบังคับภาพหรือเอกสารก่อนรับรองตามนโยบายที่ผู้จัดอนุมัติ
- ภาพ ลายเซ็น และรายละเอียดส่วนตัวเก็บเฉพาะพื้นที่จำกัดสิทธิ์ ไม่บรรจุใน repo สาธารณะหรือ JSON เผยแพร่
- ภาพถ่ายที่ส่ง ChatGPT ไม่ถือเป็นการอนุมัติผลโดย AI และห้ามกรอกตัวเลขที่อ่านไม่แน่ใจด้วยการคาดเดา

## 4. กติกาความถูกต้องและการอนุมัติ

- ผู้ใช้งาน: กรรมการสนาม “ส่งผล”; ฝ่ายบันทึกผล “ตรวจรายการ/ขอแก้ไข”; ผู้มีสิทธิ์รับรอง “ยืนยันผล”; ประชาชน “ดูผลที่เผยแพร่แล้ว” — ไม่ให้รายชื่อในคำสั่งกรรมการฉบับร่างกลายเป็นสิทธิ์บัญชีโดยอัตโนมัติ
- ผูกผลทุกครั้งกับ `fixture_id` (คู่กีฬา) หรือ `event_id` (กรีฑา) ภายในระบบ **แต่ไม่แสดงรหัสเหล่านี้แก่ผู้ใช้ทั่วไป**; ชื่อทีม/รุ่น/สนามต้องตรงกับรายการที่ผู้จัดรับรอง
- ถ้าเคยมีผลของรายการเดียวกัน: คะแนนตรงกันให้แจ้งว่ามีบันทึกแล้ว; คะแนนต่างกันให้ส่งเข้าคิวตรวจ; ผลที่รับรองแล้วห้ามเขียนทับเงียบ ๆ ต้องแก้ไขผ่าน revision, ผู้ตรวจ และเหตุผล
- จัดสถานะในระบบ: draft/review/approved/corrected; ข้อมูลสาธารณะมีเฉพาะ approved; ต้องรักษาประวัติผู้บันทึก ผู้ตรวจ เวลาบันทึก และรายละเอียดการแก้ไขในพื้นที่ภายใน
- ตัวส่งออก Apps Script ตรวจสิทธิ์ผู้รับรอง, ตรวจการแก้ไขหลังรับรอง/ลายพิมพ์ข้อมูล, ตรวจต้นทางรายการแข่งขัน, ตรวจความครบของอันดับกรีฑา และไม่ส่งออกผลที่ยังขัดกัน
- การส่ง GitHub ต้องจำกัดสิทธิ์โทเคนเฉพาะ repo, เก็บความลับในพื้นที่ส่วนตัวที่จัดการสิทธิ์ได้, ไม่ใส่ token/URL เขียนข้อมูลใน HTML/JS/เซลล์/JSON สาธารณะ; เริ่มด้วยกดส่งและ PR ที่ต้องตรวจ Merge ก่อน ค่อยพิจารณาการสร้าง PR อัตโนมัติเมื่อ QA ผ่าน
- ส่งซ้ำต้องไม่สร้างผลซ้ำหรือ PR ซ้ำโดยไม่จำเป็น; ต้องตรวจเนื้อหา/รุ่นล่าสุดของไฟล์ก่อนอัปเดต และรับมืออินเทอร์เน็ตขาดโดยไม่ลบข้อมูลที่กรอก

## 5. ข้อกำหนดประสบการณ์ผู้ใช้: **ภาษาทั่วไป ไม่ใช้ศัพท์เทคนิค** (สำคัญ / บังคับ)

> ผู้ใช้หลักเป็นคุณครู กรรมการสนาม เจ้าหน้าที่โรงเรียน และผู้ชมการแข่งขัน ไม่ใช่ผู้พัฒนาระบบ ทุกหน้าที่แสดงแก่ผู้ใช้ทั่วไปต้องสื่อว่า **กำลังทำอะไร**, **สำเร็จหรือยัง**, **ต้องทำอะไรต่อ** โดยไม่ต้องรู้จักเครื่องมือเบื้องหลัง

### 5.1 หลักการเขียนข้อความ

1. ใช้ภาษาไทยธรรมดา ประโยคสั้น สุภาพ สื่อการกระทำ; ปุ่มเน้นคำกริยา เช่น **บันทึกผล**, **ส่งผลให้ตรวจ**, **ตรวจรายการ**, **ยืนยันผล**, **ดูผลการแข่งขัน**, **ลองอีกครั้ง**
2. ไม่แสดงศัพท์พัฒนา เช่น `JSON`, `API`, `Apps Script`, `GitHub`, `PR`, `Pull Request`, `CI`, `schema`, `digest`, `fixture_id`, `event_id`, `token`, `null`, `403/500` หรือรหัสเครื่องจักรในข้อความ หน้าเมนู และ toast สำหรับประชาชน/กรรมการทั่วไป
3. แสดงชื่อกีฬา รุ่น คู่แข่งขัน โรงเรียน วัน เวลา และสถานะที่คนอ่านรู้เรื่อง แทนการให้พิมพ์รหัสคู่แข่งขัน
4. ข้อผิดพลาดบอกสาเหตุที่ผู้ใช้พอเข้าใจและสิ่งที่ทำต่อได้ ไม่พ่น trace หรือรายละเอียดระบบลงหน้า; รักษาข้อมูลในฟอร์มเสมอ
5. ใช้ศัพท์สถานะอย่างสม่ำเสมอ: **กำลังบันทึก**, **บันทึกแล้ว รอตรวจสอบ**, **ส่งกลับให้แก้ไข**, **ยืนยันผลแล้ว**, **แสดงผลบนเว็บไซต์แล้ว**; อย่าใช้ `approved / review / published` ในส่วนหน้าบ้าน
6. ให้หน้าจอเป็น mobile-first กดง่าย ใช้ฟอร์มไม่ยาวเกินไป และแสดงเฉพาะช่องจำเป็นตามกีฬา; ไม่บังคับแนบภาพในกรณีปกติ
7. เก็บข้อมูลเทคนิคไว้ในโค้ด, log จำกัดสิทธิ์ และคู่มือผู้ดูแลเท่านั้น; เมนูใน Sheets ที่กรรมการใช้อยู่ต้องเรียก **“ตรวจและยืนยันผล”**, **“ส่งผลขึ้นเว็บไซต์”**, **“ดูประวัติการส่ง”** แทนคำเทคนิค
8. ปิดรายละเอียดเชิงเทคนิคแก่ผู้ใช้ทั่วไป แต่ต้องไม่ปิดบังข้อเท็จจริงเรื่องสถานะ/ความผิดพลาด/ข้อมูลที่ยังไม่ได้รับรอง

### 5.2 ตัวอย่างการปรับถ้อยคำ

| ไม่ใช้กับผู้ใช้ทั่วไป | ใช้แทน |
| --- | --- |
| Export approved JSON / Push GitHub | ส่งผลที่ยืนยันแล้วขึ้นเว็บไซต์ |
| Update `public-results.json` สำเร็จ | ส่งข้อมูลสำหรับเผยแพร่เรียบร้อย |
| HTTP 403 / Unauthorized | บัญชีนี้ยังไม่ได้รับสิทธิ์บันทึกผล กรุณาติดต่อผู้ดูแล |
| Validation failed / Invalid fixture_id | กรุณาตรวจคู่แข่งขันและคะแนนอีกครั้ง |
| API timeout / Network error | เชื่อมต่อไม่สำเร็จ ข้อมูลที่กรอกยังอยู่ กรุณาลองอีกครั้ง |
| Duplicate result / Conflict | มีผลของคู่นี้บันทึกไว้แล้ว กรุณาตรวจสอบก่อนส่งอีกครั้ง |
| Status: review | ส่งผลแล้ว รอตรวจสอบ |
| Status: approved | ยืนยันผลแล้ว |
| PR pending CI | ส่งผลแล้ว กำลังตรวจสอบก่อนแสดงบนเว็บไซต์ |
| Empty approved dataset | ยังไม่มีผลการแข่งขันที่ยืนยันและเผยแพร่ |

**ข้อความสำคัญ:** แยกสถานะ “บันทึกสำเร็จ” ออกจาก “ยืนยันผลแล้ว” และ “เผยแพร่แล้ว” อย่างชัดเจน เพื่อไม่ทำให้กรรมการเข้าใจว่ากดส่งแล้วประกาศผลทันที.

### 5.3 เกณฑ์ตรวจรับด้านภาษาและความง่าย

- ผู้ใช้ทั่วไปสามารถทำงานได้ด้วยคำสั่งบนหน้าจอโดย **ไม่ต้องเข้าใจ Google Sheets, Apps Script หรือ GitHub**
- ตรวจข้อความปุ่ม, หัวข้อ, ช่องกรอก, empty state, loading, toast, validation, error, confirmation, share, และข้อความหลังส่งครบทุกหน้า
- ทดสอบกับครู/กรรมการอย่างน้อย 1 คนที่ไม่ใช่ผู้พัฒนาระบบ: ค้นคู่แข่งขัน → กรอกคะแนน → ส่ง → เข้าใจสถานะ และรู้ว่าจะติดต่อใครเมื่อผลถูกส่งกลับ
- ทดสอบบน iPhone Safari และ LINE in-app browser; ไม่มีข้อความตัด/ปุ่มเล็ก/แป้นพิมพ์บังปุ่ม และไม่สูญข้อมูลเมื่อสัญญาณขาด
- ศัพท์อังกฤษเชิงเทคนิคหรือรหัสภายในไม่ปรากฏในหน้าใช้งานสาธารณะ ยกเว้นจำเป็นต่อการตรวจสอบโดยผู้ดูแลที่มีสิทธิ์เท่านั้น

| R20-F | ทดสอบภาคสนามกับครู/กรรมการจริง และ QA ข้อความภาษาไทยทุกสถานะ | ใช้ได้โดยไม่ต้องรู้ศัพท์เทคนิค และแก้ไขคะแนนได้ตามสิทธิ์ |

## 7. สิ่งที่ไม่ทำในรอบแผนนี้

- ไม่เปิด API เขียนชีตจากหน้าเว็บสาธารณะโดยไม่พิสูจน์ตัวตน
- ไม่ตั้งให้ Apps Script เขียนทับ `main` และเผยแพร่ทันทีโดยข้ามตรวจรับ/PR
- ไม่แก้คะแนนจริง, ไม่สร้าง Approved ปลอม, ไม่ย้ายหรือลบระบบรูปถ่าย ChatGPT เดิม
- ไม่เปลี่ยน `results.html`, `standings.html`, `data/public-results.json` หรือ Google Sheets จริงในการบันทึกแผนครั้งนี้
