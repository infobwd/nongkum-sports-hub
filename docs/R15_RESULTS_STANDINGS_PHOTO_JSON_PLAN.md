## 2. การตัดสินใจเชิงสถาปัตยกรรม (Design lock)

**คง 2 เมนูหลักเท่านั้น** คือ ตารางแข่ง และ ผลแข่งขัน; เพิ่มปุ่ม/แท็บย่อย `ผลรายคู่ | ตารางอันดับ` ภายในบริบทผลแข่งขันให้ผู้ใช้ไป `standings.html` ได้ ไม่เพิ่มแท็บล่างที่สาม. ทั้งสองหน้าเก็บตัวกรอง `school`, `sport`, `level` เมื่อสลับ, ใช้ responsive mobile-first, deep link, loading/failure/empty state และ Safe Area ของระบบเดิม.

แยกไฟล์เพื่อไม่ขยาย `results.js` จนดูแลยาก:

| ไฟล์ (เสนอสร้างใน R15 ระยะเขียนโค้ด) | บทบาท |
|---|---|
| `standings.html`, `css/standings.css` | หน้าตารางอันดับ; สร้างเมื่อเริ่ม R15-A |
| `js/standings.js` | fetch/render/filter/refresh โดยโหลดเฉพาะเมื่อเปิดหน้าอันดับ |
| `js/standings-engine.js` | pure functions คำนวณ; ใช้ร่วมชุดทดสอบ/ตัวสร้าง snapshot; อย่าเขียนกติกาซ้ำใน UI |
| `data/standings-rules.json` | ระบุกติกาต่อกีฬา/รุ่น/phase แบบอนุมัติและมี version; **ยังไม่สร้างค่าที่สมมติ** |
| `data/public-standings.json` | *derived-only* snapshot จากผล `approved`; ไม่ให้แก้ตารางด้วยมือ |
| `scripts/results/build-standings.mjs` | validate แล้วสร้าง/ตรวจผล deterministic (`--check` ใน CI) |
| `scripts/results/validate-publication.mjs` | ตรวจความถูกต้องก่อน Merge ผลและอันดับ |
| `docs/R15_RESULTS_...QA.md` หรือคู่มือขั้นตอนจริง | สรุปการปฏิบัติหลังรอบ implementation |

**แหล่งข้อมูลหลักสำหรับผล:** `data/public-results.json` เท่านั้นสำหรับผลที่เผยแพร่แล้ว. Snapshot อันดับต้องระบุ source digest/hash และ version กติกาที่ใช้; ไม่คำนวณอันดับจากผลร่างหรือคำบรรยายในภาพโดยตรง. การเปิดหน้าผลไม่ควรต้องดาวน์โหลด JSON สูจิบัตรขนาดใหญ่โดยไม่จำเป็น. ใช้ records สำหรับโรงเรียน/กีฬาใน public-results และอนาคตจัด snapshot ให้โหลดเบา; ตรวจ consistency ใน build ไม่ใช่ให้ browser ดาวน์โหลดซ้ำ 237 รายการเพื่อ join ทุกครั้ง.

## 3. ตารางอันดับแต่ละรูปแบบ (ยังไม่กำหนดกติกาแทนคณะกรรมการ)

1. **พบกันหมด (round-robin):** ทีม/โรงเรียน, แข่ง, ชนะ, เสมอ, แพ้, ได้, เสีย, ผลต่าง, คะแนน; ระหว่างแข่งให้แสดง `ผลรับรองแล้ว x/y คู่ · อันดับระหว่างการแข่งขัน` ไม่ใช้คำว่าอันดับสุดท้าย. ต้องรับรองการให้คะแนนชนะ/เสมอ/แพ้, tie-break เช่นผลต่าง/พบกันเอง, การไม่มาลงแข่งและการตัดสิทธิ์.
2. **แพ้คัดออก (bracket):** แสดงสาย/รอบและผู้ชนะที่ยืนยัน; อันดับ 1–3 ให้ยึดผลรอบชิงและกติกาเหรียญจริง ไม่คิดคะแนน league จากคู่แบบแพ้คัดออก.
3. **กรีฑา/ประเภทจัดอันดับ:** ผล `ranking` จากรายการที่รับรองครบชุด, โรงเรียน, อันดับ, สถิติ/หน่วยที่มีจริง; ไม่เติมข้อมูลนักเรียนส่วนบุคคลใน JSON สาธารณะ.
4. **เหรียญ/คะแนนรวมโรงเรียน:** *ระยะอนาคตเท่านั้น* ต้องยืนยันเกณฑ์นับเหรียญ/การให้คะแนน (เช่น 5–3–2 หากคณะกรรมการกำหนดจริง), tie-break, รายการทีม/เดี่ยว/หลายทีม/เสมอ/ยกเลิก ก่อนเผยแพร่; ไม่เปิดตารางรวมโดยใช้กติกาที่คิดเอง.

**ข้อค้นพบต้องแก้ใน data mapping ก่อนเปิด ตารางคะแนนฟุตบอล:** ฟุตบอล 12 ปีชายใน candidate มี `round: "พบกันหมด"` **17 รายการ** แต่ 15 รายการเป็นคู่ระหว่าง 6 ทีมที่ระบุชื่อ และอีก 2 รายการคือ `คู่ 17 ทีมอันดับ 1 พบ 4`, `คู่ 18 ทีมอันดับ 2 พบ 3`. ห้ามนับ 2 คู่หลังเป็นลีกเพียงเพราะค่า `round` เหมือนกัน. ต้องสร้าง phase classification จาก fixture ID ที่ผ่านตรวจรับเฉพาะรายการ (เช่น league / playoff) ในกติกาหรือทะเบียนข้อมูลเพื่อคำนวณที่ถูกต้อง; ห้ามแก้ชื่อรอบใน PDF ต้นทางโดยไม่บันทึกการตรวจรับ.

## 4. Workflow ภาพถ่ายกระดาษ → ผลตรวจรับ → JSON → เว็บไซต์

```
ใบบันทึกผลจากกรรมการ (กระดาษ/ลงนาม)
  → ถ่ายภาพให้ชัด (เก็บในพื้นที่ส่วนตัว)
  → เจ้าหน้าที่อ่าน/ถอดคะแนนและผูก fixture_id หรือ event_id
  → ตรวจสอบกับใบบันทึก/ชื่อโรงเรียน/กีฬา/กติกา
  → ผู้รับผิดชอบรับรองผล + เก็บหลักฐานและประวัติแก้ไข (ส่วนตัว)
  → สร้าง approved-only JSON + validate + preview diff
  → PR ใน GitHub → CI → ตรวจรับ/merge
  → GitHub Pages deploy → results.html + standings.html แสดง snapshot ล่าสุด
```

- เลือก **manual-first**: ผู้ประสานงานส่งภาพใบคะแนนให้ผู้ดูแล/ChatGPT ช่วยถอดผลอย่างมีหลักฐาน; **AI ไม่ใช่ผู้รับรอง**. หากอ่านไม่ชัดให้ขอภาพ/หลักฐานใหม่ ไม่เดาตัวเลข ไม่รับรองโดยอัตโนมัติ.
- ภาพต้นฉบับ ลายเซ็น รายชื่อนักเรียน เลขโทรศัพท์ ผู้อนุมัติ อีเมล หลักฐานที่เปิดเผยข้อมูลส่วนบุคคล ให้เก็บใน Google Drive/พื้นที่ปิดที่ผู้ได้รับสิทธิ์เข้าถึง; **ห้าม commit ภาพ/PII/ลิงก์ส่วนตัว/โทเคนลง public repo**.
- ผู้ถอดผลและผู้รับรองควรเป็นคนละบทบาทเมื่อทำได้; log ภายใน: fixture/event ID, เวลาได้รับ, ผู้บันทึก, ผู้รับรอง, เวลาอนุมัติ, evidence ID/Drive link แบบไม่สาธารณะ, revision และเหตุผลแก้ไข. JSON สาธารณะไม่มีรายละเอียดผู้ลงนาม.
- ถ้าผลที่เผยแพร่แล้วต้องแก้ไข ใช้ revision ใหม่พร้อมเหตุผลและหลักฐานที่เก็บแบบส่วนตัว; ไม่ลบประวัติ/ไม่แก้ผลเงียบ ๆ. ให้ป้องกัน PR ที่ทำให้ approved result หายโดยไม่มี correction record.
- Google Sheets R3 และ `apps-script/Results.gs` เป็นเส้นทางทางเลือกในอนาคตเพื่อเข้มงวดการอนุมัติ ไม่ใช่เงื่อนไขต้องติดตั้งก่อนเริ่ม manual JSON. ทั้งสองทางต้องผ่าน validator/CI + human approval เดียวกัน.

## 5. Public result contract / Release gate (ยังไม่แก้ schema จริง)

- ใช้ `schema_version: 1` ของ `public-results.json` ปัจจุบันก่อน หากต้องเพิ่ม fields ให้ทำ schema migration พร้อม test, ไม่เขียนข้อมูลที่ไม่รองรับรูปแบบ `results.js`.
- ต้องมี id ผลไม่ซ้ำ, `fixture_id`/ `event_id` ตรงกับโปรแกรม 237 รายการล่าสุด, กีฬา/รุ่น/ทีมตรงต้นทาง, status `approved` เท่านั้น, คะแนนจำนวนเต็มไม่ลบ, สถิติและเซ็ตเป็นค่าที่สมเหตุสมผล, ผู้ชนะตรงคะแนนหรือกติกาผลเสมอ, ไม่เผยแพร่คู่ที่ยังไม่ทราบทีมจริง.
- ตรวจ event กรีฑา **ทั้งชุดอันดับ** ก่อนส่งออก ไม่แสดงอันดับครึ่งชุดเป็นอันดับสรุป; validate การซ้ำของอันดับ/โรงเรียนและหน่วยสถิติที่เหมาะสม.
- ถ้าผลร่าง/ภาพไม่สมบูรณ์ ให้ค้างสถานะส่วนตัวและปล่อยหน้าเว็บแสดง `ยังไม่มีผลรับรอง` สำหรับรายการนั้น. ห้ามทำข้อมูลสมมติเป็นสาธารณะ แม้เพื่อสาธิต UI.
- `public-standings.json` ให้ตัวสร้างจาก `public-results.json` deterministic, มี source digest, rules_version, generated_at, ตารางเฉพาะที่กติกาได้รับรอง และสถานะ `partial/final`; ตรวจ mismatched/stale snapshot ไม่ให้แสดงอันดับผิด.
- การกด Refresh ใช้ fetch JSON ที่ deploy แล้วพร้อม cache-busting และ fallback คงข้อมูลก่อนหน้าหากเครือข่ายล้มเหลว; ไม่อ้างว่าอัปเดตเรียลไทม์จากกรรมการ/Google Sheets.

## 7. งานคู่ขนาน: อีกแชทปรับการเรียงตารางแข่งขัน

แยกสาขา/PR จาก R15 เพื่อหลีกเลี่ยง conflict. อีกแชทแก้เฉพาะ `index.html`/`js/program.js`/`css/program.css` และ regression ที่เกี่ยวข้องตามสมควร; **R15-0 เป็น docs-only** ไม่แตะไฟล์เหล่านั้น.

แนวทางเรียงหน้าตารางที่เสนอ: **วันแข่งขัน → เวลา → กีฬา/รุ่น → เลขรายการ/ID (stable tie-break)** โดยแสดงการแบ่งหัวกลุ่มวันให้เลื่อนใช้งานง่าย; เมื่อกรองโรงเรียน/กีฬาแล้วให้คงลำดับเดียวกัน. รายการที่มีวันแต่ไม่มีเวลาอยู่ท้ายวันนั้น; รายการที่วันขาด/ปีผิดปกติ/ยังไม่ยืนยันให้อยู่กลุ่ม `รอยืนยันวันและเวลา` แยกท้ายรายการ และ **อย่าใช้วันที่ ISO ที่ถูกสมมติให้ทับข้อความปีผิดปกติใน PDF**. รายการที่กำหนดวันด้วยประกาศที่รับรองควรใช้ effective date ที่มี provenance/confirmation ก่อนค่าร่าง; ห้ามแก้ไข candidate ต้นฉบับเงียบ ๆ. การเรียงเป็นการเปลี่ยน **presentation order** ไม่ใช่แก้ fixture ID, URL, short links, scorecard links, PDF page หรือสถานะผล.

หากอีกแชทกำลังแก้ไฟล์ในสาขาของตัวเอง ให้ merge แยก PR และ rebase/ตรวจ latest main ก่อน merge; แผน R15 ใช้ ID เดิมได้ ไม่ควรผูก logic ตารางอันดับกับตำแหน่งของรายการที่แสดง.

## 8. รายการตัดสินใจที่ยังต้องขอจากคณะกรรมการก่อนเขียน engine จริง

- เกณฑ์คะแนนฟุตบอลพบกันหมด (ชนะ/เสมอ/แพ้), tie-break, กรณีไม่มาแข่ง/ปรับแพ้, ผลแข่ง 15 คู่ และการเข้ารอบ 4 ทีม
- เงื่อนไขประกาศอันดับสุดท้ายของกีฬาแพ้คัดออก, ผู้ได้อันดับ 3 ร่วม, ระบบจัดเหรียญ และกรณีทีมถอนตัว
- ผลกรีฑาวัดตามหน่วย/วิธีเรียงเวลา-ระยะ, กรณีผลเท่ากันและแถวอันดับไม่ครบ
- หากมีคะแนนรวมโรงเรียน: นิยามเหรียญ/แต้มและวิธีนับต่อกิจกรรม/ช่วงชั้น; ไม่ใช้สมมติฐาน 5–3–2 เอง
- ผู้รับรองผลจริง, ผู้แก้ไข JSON และช่องทางเก็บภาพต้นฉบับส่วนตัว
