## 3. ข้อมูลส่วนบุคคลและขอบเขตการเผยแพร่ (Hard Gate)

1. **พื้นที่เก็บจริงต้องเป็น Private Repository ที่แยกต่างหากหรือ Drive/ระบบภายในที่จำกัดสิทธิ์** โดยเจ้าของต้องตั้งสิทธิ์ก่อนนำข้อมูลเด็กเข้า; ใช้หลักเก็บข้อมูลเท่าที่จำเป็น. ยังไม่มีการสร้างพื้นที่ดังกล่าวจากแผนนี้
2. ภาพกระดาษ ชื่อ–สกุล วันเกิด ชื่อเล่น เลขประจำตัว รูป QR หรือ mapping `athlete_id ↔ ชื่อ` **ห้าม commit ไป `infobwd/nongkum-sports-hub` ซึ่งเป็น public repo**; ห้ามวางใน PR, issues, actions logs หรือ JSON ที่ browser ดาวน์โหลดได้
3. หากเก็บไฟล์รายบุคคลใน private repo ต้องตรวจสิทธิ์สมาชิก นโยบายเก็บรักษา การลบข้อมูลภายหลังการแข่งขัน การสำรองข้อมูล และการรั่วผ่าน Git history; ลบไฟล์จาก HEAD ไม่เท่ากับลบประวัติ. ถ้าไม่มั่นใจใช้ Drive จำกัดสิทธิ์เป็นหลัก
4. ใน Public Repo อนุญาตเฉพาะ **schema ตัวอย่างสมมติ, กติกา, โค้ด, และสรุประดับรายการ/กีฬา** โดยไม่แสดงรหัสบุคคลที่เชื่อมกลับได้หรือรายละเอียดกลุ่มเล็กที่อาจระบุตัวเด็ก
5. ห้ามส่งภาพเด็ก/ชื่อไป third-party OCR, logs หรือเว็บไซต์อิสระโดยพลการ; การใช้แชทสำหรับข้อมูลส่วนตัวต้องเป็นช่องทาง/บัญชีที่ผู้จัดอนุญาตและปฏิบัติตามนโยบายของสถานศึกษา

## 4. รูปแบบการรับภาพและการยืนยันข้อมูล

- บันทึก `school_id`, รหัสเอกสารภายใน, หน้า/ลำดับแถว, วันที่รับเอกสาร และจำนวนหน้าที่ควรมี เพื่อเช็กเอกสารครบ
- ถอด `name_raw` ตามที่เห็นและ `name_reviewed` หลังตรวจ รวม `sport_id`, รุ่นอายุ/เพศ, ทีม, บทบาทผู้เล่น/ตัวสำรอง, รายการที่ระบุบนกระดาษ และตำแหน่งต้นฉบับ
- กรณีภาพเอียง/เบลอ/ชื่อไม่ครบ ให้ `extraction_status=needs_review` และแสดงความไม่แน่นอน; **ไม่สร้างชื่อ, ไม่สร้างเลขบัตร, ไม่เติมผู้เล่นจากการเดา**
- ตรวจความซ้ำ: ชื่อคล้าย/สะกดต่างกัน, คนชื่อเหมือนกันคนละโรงเรียน, คนเดียวกันอยู่หลายกีฬา; ใช้ `school_id` และหลักฐาน/เจ้าหน้าที่รับรอง ไม่ merge ชื่อซ้ำอัตโนมัติ
- เจ้าหน้าที่ตรวจทานข้อมูลแต่ละโรงเรียนครบหน้าและจำนวนชื่อ; ออก `athlete_id` ที่คงที่ภายในโรงเรียน **หลังยืนยันว่าเป็นบุคคลเดียวกัน**
- บันทึกสถานะ `received → extracted → needs_review → school_checked → accepted_for_analysis`; ติดตามเอกสารที่ยังไม่มา ไม่อ้างว่า “ปลอดความขัดแย้ง” ถ้าข้อมูลไม่ครบ

### ตัวอย่าง logical schema (ข้อมูลสมมติเท่านั้น; สำหรับ private storage)

```json
{
  "athlete_id": "EXAMPLE-SCHOOL-A001",
  "school_id": "example_school",
  "display_name_private": "ตัวอย่าง สมมติ",
  "registrations": [
    {
      "sport_id": "football",
      "division": "12 ปี ชาย",
      "team_ref": "EXAMPLE-TEAM-1",
      "role": "player",
      "linked_fixture_ids": [],
      "match_status": "needs_review"
    },
    {
      "sport_id": "athletics",
      "event_id": "EXAMPLE-EVENT-1",
      "lane": null,
      "match_status": "needs_review"
    }
  ],
  "source_refs_private": ["EXAMPLE-DOC-01:p2:r5"],
  "extraction_status": "school_checked"
}
```

**หมายเหตุ:** กีฬาประเภททีมต้องเชื่อมทั้ง roster กับทีม/สาย แล้วขยายการเข้าร่วมเป็นทุกคู่ที่เกี่ยวข้อง, ไม่จำเป็นต้องให้กรอกชื่อซ้ำรายคู่. รอบ `ผู้ชนะคู่…` เป็นความเสี่ยงแบบมีเงื่อนไข ไม่ถือว่าเด็กทุกทีมเล่นแน่นอน. ตัวสำรองควรนับเป็น “อาจถูกเรียก” ตามกติกาที่กรรมการกำหนด. `linked_fixture_ids` จะเติมจาก stable fixture ID จริงหลังตรวจ mapping.

## 5. โมเดลเวลาที่ใช้วิเคราะห์

แต่ละรายการมี `date`, `start`, `expected_duration`, `check_in_lead`, `expected_finish`, `venue`, `field/court`, `transition_travel`, `minimum_rest`, `delay_buffer`, `time_confidence` และ `source_revision`. ค่าเวลาต้องให้กรรมการกีฬาเป็นผู้กำหนดตามชนิดกีฬา/รุ่น/รอบ (ไม่ใช้ค่าตัวอย่างเป็นเกณฑ์จริง)

- **Hard conflict:** นักกีฬาเดียวกันมีช่วงรายงานตัว–แข่งขันทับซ้อน หรือไม่สามารถเดินทางระหว่างสนามในเวลาที่มี; ตรวจสนาม/คอร์ต/กรรมการใช้ซ้ำในช่วงเดียวกันอีกชั้น
- **Near conflict:** ไม่ทับกันในนาฬิกาแต่ไม่มีเวลาเดินทาง/พัก/เวลาเผื่อเพียงพอ
- **Potential / unknown:** โรงเรียนเดียวกันลงหลายกีฬาเวลาใกล้กันแต่ยังไม่มี roster, เวลาไม่มี, mapping ชื่อไม่แน่, รอบก่อนหน้ายังไม่ทราบผู้ชนะ
- **No conflict (conditional):** ให้แสดงได้เฉพาะขอบเขตที่ roster ครบ ชื่อรับรอง การ mapping สำเร็จ และมีข้อมูลเวลาเพียงพอ; แสดง coverage/unknown ควบคู่ทุกครั้ง

ตัวอย่างเบื้องต้นจากการจัดกลุ่ม `school_id + draft_date + draft_time` พบ **33 กลุ่มเวลาที่โรงเรียนเดียวกันมีรายการเริ่มพร้อมกัน** ใน candidate; เป็นเพียง *school-level screening* ไม่ใช่ 33 นักกีฬาชนจริง: กีฬาชาย/หญิงและรุ่นอายุไม่จำเป็นต้องใช้คนเดียวกัน. R12A สร้าง [deterministic report](R12A_SCHOOL_TIME_RISK_REPORT_2569.md) และตรวจนับซ้ำแล้ว: 33 กลุ่มเวลาเริ่มตรงกัน, 96 คู่เริ่มห่างไม่เกิน 30 นาที, 53 รายการขาดวันหรือเวลาเริ่ม; ทั้งหมดเป็น screening ไม่ใช่ความขัดแย้งระดับบุคคล

## 6. ตัวเสนอแก้ตาราง (Decision Support / ไม่มี auto-publish)

1. แสดงรายการที่เกี่ยวข้องกับเด็กคนเดียวกันเฉพาะใน private operator view; อธิบายว่า overlap ตรงเวลา, check-in, travel, rest, หรือ unknown
2. เสนอ **สลับลำดับคู่ภายในชนิดกีฬาเดียวกัน** ก่อน ถ้ากฎรอบ สาย สนาม กรรมการ และความพร้อมคู่ใหม่ยังผ่าน
3. หากไม่ผ่าน เสนอขยับเวลา/ช่องสนามที่ว่าง; ถ้าจำเป็นจึงเสนอเปลี่ยนช่วง/วันตามข้อจำกัดที่กรรมการยืนยัน
4. คำนวณผลกระทบต่อ **ทุกคู่ในวันนั้น**, ทั้งทีม, สนาม, กรรมการ, ช่วงพัก, รอบถัดไป, เวลาเปิด–ปิด, ภาระงานผู้บรรยาย; หากยังมี conflict ต้องแสดง ไม่ซ่อนเพราะคะแนนทางเลือกดี
5. แสดงก่อน–หลัง: conflict ที่ลดลง, conflict ใหม่ที่เกิด, จำนวนคู่ที่เปลี่ยน, นาทีที่ขยับ, ข้อจำกัดที่ยังไม่ทราบ, และเหตุผลที่แนะนำ
6. เขียนเป็น `proposed_schedule_change` แยกจาก source/approved data พร้อม revision, diff, ผู้ตรวจ, มติ; **กรรมการอนุมัติจึงผ่าน R11E** ไปยังเว็บ/Docs และระบบเรียกนักกีฬา R10 ใช้ approved snapshot แบบ read-only

ข้อจำกัดแข็ง: ไม่เปลี่ยนวัน/สถานที่ที่ยืนยันเฉพาะฟิลด์โดยไม่มีมติ, ไม่ทำให้รุ่น/สาย/ผู้ชนะผิด, ไม่บังคับให้นักกีฬาต้องแข่งสองสนามพร้อมกัน และไม่อ้างว่าแก้ conflict ได้หมดถ้า roster/เวลาไม่ครบ
